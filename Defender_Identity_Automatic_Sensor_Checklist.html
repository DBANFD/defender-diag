Identity / Rollout checklist

Reviewing automatic Defender for Identity sensor activation

Check eligibility, auditing changes, policy conflicts, and evidence before the rollout reaches identity-role servers.

Understand the rollout

Microsoft is gradually enabling Automatic sensor v3.x activation and Automatic Windows auditing configuration for eligible existing Defender for Identity workspaces after a 30-day portal notice. This can include settings that are currently off. An eligible organization can opt out from the banner during that notice period. The two controls are separate. See Defender for Identity what's new.

Automatic activation targets eligible identity-role servers already onboarded to Defender for Endpoint. It activates the v3 sensor capability rather than installing a separate sensor package, and it doesn't target servers that already have a Defender for Identity sensor. Eligible servers require Windows Server 2019 or later. Activation on AD FS, AD CS, and Microsoft Entra Connect servers that aren't domain controllers remains preview; do not treat that scope as generally available. Activation prerequisites and scope.

Inventory eligible servers

  1. List domain controllers, AD FS, AD CS, and Microsoft Entra Connect servers.
  2. Record OS version, Defender for Endpoint onboarding state, existing Defender for Identity sensor version, server owner, and maintenance constraints.
  3. Identify Server 2016 or earlier systems that require the v2 sensor path instead of v3.
  4. Confirm Defender for Identity licensing and workspace status before interpreting the banner.

Do not infer eligibility from a server role alone. Compare each server with the current sensor v3 prerequisites and limitations.

Review automatic auditing

Automatic auditing checks and applies supported local audit settings once every 24 hours. Depending on server role, this can include advanced audit policy, NTLM auditing, domain and Configuration partition SACLs, AD FS or AD CS settings, and Entra Connect logon auditing. GPO can conflict with settings applied locally by the sensor.

AD CS needs special attention: automatic auditing modifies an existing CA audit filter but does not create one, and the new value takes effect only after the Certificate Services service restarts. Other AD FS settings can remain manual. Review the exact role-specific scope in Configure Windows event auditing.

Make the decision explicit

DecisionUse whenRequired follow-up
Enable nowEligibility, policy ownership, network paths, and audit effects are understood.Pilot a small identity-role scope and monitor sensor health and event collection.
Allow gradual enablementThe same checks are complete and the rollout timing is acceptable.Record the 30-day notice window and responsible owner.
Opt outThere is a documented policy conflict, unsupported scope, change freeze, or unowned operational risk.Keep required auditing and sensor coverage through the supported manual path, and set a review date.

An opt-out is not a substitute for Defender for Identity coverage. Document how eligible servers remain monitored and how required Windows events are collected.

Verify after activation

  • In Defender portal Sensor management, confirm the expected server appears and reaches Running. Microsoft notes the first v3 activation can take up to an hour; later activations can appear within five minutes.
  • Review Defender for Identity health alerts for incorrect or missing event auditing.
  • Check that GPO does not revert required local audit settings.
  • For AD CS, coordinate the required Certificate Services restart and confirm health afterward.
  • Record server, sensor state, activation time, audit-policy result, health alerts, and owner. Do not use a green sensor state alone as proof that every required event is being collected.
