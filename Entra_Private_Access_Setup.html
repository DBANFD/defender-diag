Setting up Microsoft Entra Private Access

A practical field note for publishing private applications and RDP access through Microsoft Entra Private Access and Global Secure Access.

Start with one application

Microsoft Entra Private Access provides identity-controlled access to private resources through Global Secure Access. For a first pilot, publish one application to one small user group, then validate access decisions, connectivity, and recovery before expanding.

Example: Publish rdp01.corp.example.com on TCP 3389 through a dedicated application segment. Private Access authorizes the connection path; the Windows target still authenticates the RDP user.

Plan the required Entra ID P1/P2 prerequisite and an Entra Private Access or Entra Suite license for the relevant users. See traffic forwarding and licensing requirements.

Place connectors where they can reach the target

Use supported Windows Server hosts with the required .NET and TLS configuration, outbound access to Microsoft's connector services, and internal connectivity to the application. Connectors must resolve the backend name and reach its port. Follow the current endpoint allowlist rather than assuming outbound HTTPS alone covers every dependency.

Use at least two healthy connectors in the production connector group for resilience. Avoid making both dependent on the same single failure point. Keep them updated and monitor their status. Microsoft's connector installation guidance specifies the supported prerequisites. Do not apply Application Proxy-only changes, such as disabling HTTP/2, to a Private Access-only deployment without a relevant requirement.

Configure per-app access and assignment

  1. Create the Global Secure Access application with the required administrator roles.
  2. Select the connector group that can reach the backend.
  3. Add the narrow application segment: target FQDN or address, protocol, and required port.
  4. Assign the pilot users or group to the enterprise application.
  5. Enable and assign the Private Access traffic forwarding profile, and deploy the supported Global Secure Access client.

Application assignment and traffic forwarding are separate requirements. Prefer a narrow per-app segment for this pilot; avoid broad overlapping ranges that make routing and policy ownership difficult to reason about. Follow per-app access setup and Private Access profile management. A preview profile feature is not a prerequisite for this basic design.

Apply Conditional Access to the application

Target the Global Secure Access application, or the Quick Access application if that is the design. Conditional Access for Private Access is applied at application level, not to the Private Access traffic forwarding profile.

Begin with report-only policy and review sign-in results. If requiring MFA and device compliance, configure the intended combination explicitly. Selecting multiple grant controls with “require one” does not enforce all of them. Test the exact policy with both eligible and ineligible devices before enabling it broadly.

The service depends on supported client behavior. Current limitations include local-subnet IP traffic, unsupported secure DNS configurations on Windows, and interactions with DNS policies. Review the current Global Secure Access limitations before selecting an RDP, shared-device, or remote-network deployment pattern. Do not weaken DNS settings across the estate to troubleshoot one pilot.

Prove the access boundaries

  • From an assigned user's supported client, confirm the traffic profile is active, the name resolves as expected, and the application works.
  • Check the applicable sign-in, Conditional Access, and traffic records for that connection.
  • Confirm an unassigned user is denied, and test the device requirement with a nonqualifying pilot device.
  • Test connector failure and recovery without interrupting both connectors simultaneously.
  • Check that unrelated applications remain reachable through their intended paths.

Publishing an application does not remove existing VPN or local-network routes. If access must occur only through Private Access, separately design and validate the network controls that close alternative paths.

Before rollout, record how to restore previous client/profile assignments and application policy. Keep an approved administrative recovery path available during the pilot. Expand by application after the evidence supports the intended access boundary.
