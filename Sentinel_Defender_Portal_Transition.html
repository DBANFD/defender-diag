Plan around the support date

Microsoft Sentinel is generally available in the Defender portal, including for organizations without Defender XDR or an E5 license. Microsoft says Azure portal support ends after 31 March 2027, when Sentinel will be available only in the Defender portal. Portal transition overview.

Treat this as an operational change. A workspace appearing in the new portal does not demonstrate that every analyst workflow and downstream integration behaves as expected.

Build a small readiness inventory

  • Access: list analyst roles, workspace scope, and the tasks each role must perform.
  • Daily work: capture how the team searches, triages, assigns, investigates, and closes incidents.
  • Automation: identify rules, playbooks, ticket integrations, and scripts that inspect incident properties.
  • Navigation: find saved links and runbooks that send analysts to the old experience.

For each item, record an owner, expected result, observed result, and follow-up. Start with the workflows needed during an active incident, then cover less frequent administration tasks.

Review automation assumptions

Correlation can change incident titles and combine signals. Microsoft recommends avoiding incident-title conditions; review analytics-rule names and tags where appropriate. Also inspect conditions that use the Updated by field: values differ, including replacement of the old Microsoft 365 Defender value with Other.

Microsoft incident creation rules are not supported in the Defender portal. Create automation from the Automation page rather than relying on the Azure portal incident-page shortcut. Microsoft documents that forwarding can introduce up to ten minutes before an incident triggers automation. Detailed transition guidance.

Read the complete transition checklist for current prerequisites and feature differences. Rewrite a rule only after identifying what its original condition was intended to detect.

Rehearse one incident end to end

  1. Select a controlled test case with a known expected routing and response.
  2. Confirm that the intended analyst can find the incident and inspect its evidence.
  3. Check assignment, tags, automation execution, and the resulting ticket or notification.
  4. Update and close the incident; verify downstream state and watch for duplicate tickets.
  5. Record event times at each step so a delivery delay is distinguishable from a failed rule.

Use the results to update the runbook and train the next shift. Keep unresolved access, coverage, or automation issues visible until they have an owner and a verified correction.
