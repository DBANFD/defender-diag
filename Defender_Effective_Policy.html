Defender policy says “Succeeded”. Is the setting effective?

Compare policy reporting, local configuration, and running protection before closing an antivirus policy issue.

Define what success means

A green policy status is useful evidence, but it answers only part of the operational question. For a particular endpoint, did the intended setting arrive, does the current configuration match, and is the relevant protection actually running?

This workflow covers Windows endpoints with the Defender PowerShell module. Run local checks from elevated Windows PowerShell. Decide first whether Defender should be the primary antivirus or intentionally passive. The expected result depends on that design.

Synthetic scenario: An administrator expects real-time protection on a lab endpoint. A policy reports success, but local status reports it disabled. That discrepancy is a starting point, not proof that the policy service is broken.

Collect a narrow local snapshot

Download the read-only PowerShell collector · Inspect source

Inspect the script, then run it locally. It reads selected status and preference fields and prints an object. It does not change settings or export exclusions, hostnames, or user names.

.\Get-DefenderSnapshot.ps1 | ConvertTo-Json -Depth 4

The collector reports Unavailable when a read fails. Missing properties remain empty. Neither condition means protection is healthy. To obtain the underlying error during local troubleshooting, run the relevant cmdlet directly.

Get-MpComputerStatus reports antimalware status. Get-MpPreference reports configuration preferences. Compare both rather than treating them as interchangeable.

Read the fields together

QuestionEvidenceInterpretation
What mode is running?AMRunningModeCompare with the intended active/passive design; investigate an unexpected mode.
Is real-time protection operating?RealTimeProtectionEnabledA false value requires explanation when active protection is intended.
What is the local preference?DisableRealtimeMonitoringThis is negatively named: False does not request disabling real-time monitoring. It alone does not prove runtime protection.
Could protection block a change?IsTamperProtectedReview supported management and troubleshooting procedures. Do not disable protection merely to make a policy report green.
How current is the evidence?Collection time, platform version, signature timestampRecord these beside the policy report time; do not compare observations as if they were simultaneous.

Example reasoning: DisableRealtimeMonitoring=False with RealTimeProtectionEnabled=False means the selected preference does not explain the inactive runtime state. Check mode, feature availability, service health, and events before changing policy.

Find the setting owner

Identify every management path applying the specific setting: MDE security settings management, Intune, Group Policy, Configuration Manager, or local configuration. Inspect the device's Effective settings view where available, plus assignment and per-setting results in the management service. Record the source and timestamp.

Microsoft describes a general precedence order, but it also documents exceptions and shared configuration paths. Do not assume a single blanket “MDM always wins” rule. Prefer the supported Defender cmdlets over inferring effective settings from registry values; some MDE-managed exclusion values are no longer readable directly there. Follow Microsoft’s settings troubleshooting procedure.

For the lab scenario, maintain a short comparison: expected value, assigned source, reported value, local preference, runtime status, and next diagnostic. Resolve an actual conflict at its management source rather than repeatedly applying a local override.

Verify the correction

  1. Make one scoped change through the intended management tool.
  2. Allow its documented delivery cycle and any required restart; collect a new snapshot.
  3. Check the affected setting and runtime field again, then confirm fresh portal reporting.
  4. Use the feature's approved validation procedure if behavioral proof is required. A successful command or status field is not an end-to-end prevention test.

If the problem is an inactive Server 2016 engine, continue with the Server 2016 diagnostic path. Keep actual snapshots private: even this limited output describes an endpoint's protection state.
