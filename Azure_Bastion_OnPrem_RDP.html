Reaching on-premises servers with Azure Bastion

A practical field note for using Azure Bastion IP-based connection to reach an on-premises Windows host over private network connectivity.

Use Bastion as the RDP entry point

Azure Bastion can reach an on-premises Windows server by private IP when the Bastion virtual network has connectivity through a site-to-site VPN or ExpressRoute private peering. The target does not need a public IP.

Traffic path: Administrator → Azure Bastion → private connectivity → on-premises RDP target.

This pattern requires Standard or a higher supported SKU and IP-based connections enabled. IP-based RDP does not support Microsoft Entra authentication. Use credentials accepted by the target Windows server. Forced tunneling through a VPN or an ExpressRoute-advertised default route is unsupported for this design; user-defined routes on AzureBastionSubnet are also unsupported. See Bastion IP-based connections and limitations.

Check the complete path

  • Verify the private connection and return routing between the Bastion network and the target.
  • Allow the intended RDP traffic from the Bastion subnet through intermediate and Windows firewalls. Avoid opening RDP to the internet.
  • Confirm Remote Desktop is enabled and the target account has remote sign-in rights.
  • Confirm the administrator can access the Bastion resource and select the correct subscription.

If an NSG protects AzureBastionSubnet, preserve every required Bastion control-plane and service rule, not just the target RDP rule. Use the documented Bastion NSG rules and adapt target-side rules to the actual private network. Keep firewall changes narrow and record the original configuration.

Connect from the portal or native client

In the Bastion resource's connection page, choose an IP-address connection, enter the target's private address, and select RDP with the target's supported credentials. A successful Azure sign-in does not grant a Windows logon on the target.

For the native Windows client, enable native client support on Bastion and install a supported Azure CLI version (Microsoft documents 2.32 or later). Replace all placeholders, then run in PowerShell:

az login
az account set --subscription "<subscription-id>"
az network bastion rdp --name "<bastion-name>" --resource-group "<resource-group>" --target-ip-address "<private-ip>"

IP-based native connections do not support custom ports or protocols. Use the documented RDP path on TCP 3389 and check the current native Windows connection requirements.

Distinguish network failure from logon failure

  1. Confirm the private circuit or tunnel is healthy and the target and return routes are present.
  2. Inspect firewall logs for the expected Bastion-subnet-to-target flow.
  3. If the RDP session reaches Windows but authentication fails, investigate account format, rights, and Windows logon events.
  4. Complete a test session with an authorized pilot user and confirm a user without access cannot use the same route.

A test from an ordinary Azure VM is useful evidence for that VM's path, but it does not prove Bastion's subnet rules and routing are correct. Keep those checks separate. After testing, remove temporary rules and accounts, then confirm the intended access still works.
