Use the right data and scope

Download all five KQL queries · Inspect source

Run these in Microsoft Defender XDR Advanced Hunting with permission to query the relevant devices and tables. They require MDE data, available retention, and a time range that covers the query. A table-access or schema error must be resolved before interpreting the result.

The download contains five independent blocks. Select one entire numbered block, including its let statements, at a time. Replace the example device name in query 1. Use its verified DeviceId in queries 2–5. Do not paste an Entra device ID into that field.

These are investigation helpers, not production detection rules. They deliberately avoid automatic judgments about compromise or sensor health.

1. Resolve device identity

let TargetName = "lab-win-01.example.com";
DeviceInfo
| where Timestamp > ago(7d)
| where DeviceName =~ TargetName
| summarize arg_max(Timestamp, *) by DeviceId
| project Timestamp, DeviceId, DeviceName, AadDeviceId, OSPlatform
| order by Timestamp desc

A name can correspond to more than one MDE identity. Keep all returned identities until you have reconciled the current endpoint. arg_max selects the most recent available record per service device ID within this query's window; it does not certify current connectivity. No match means no matching visible record in that scope.

Microsoft documents DeviceId and AadDeviceId separately in the DeviceInfo schema.

2. Compare latest observed records

let TargetId = "REPLACE_WITH_MDE_DEVICE_ID";
let StartTime = ago(7d);
union
 (DeviceInfo | where Timestamp > StartTime and DeviceId == TargetId
  | summarize Rows=count(), LastObserved=max(Timestamp) | extend Source="DeviceInfo"),
 (DeviceProcessEvents | where Timestamp > StartTime and DeviceId == TargetId
  | summarize Rows=count(), LastObserved=max(Timestamp) | extend Source="DeviceProcessEvents"),
 (DeviceNetworkEvents | where Timestamp > StartTime and DeviceId == TargetId
  | summarize Rows=count(), LastObserved=max(Timestamp) | extend Source="DeviceNetworkEvents")
| project Source, Rows, LastObserved

Compare the three rows, rather than calling the device fresh because one table has a recent record. A zero count and empty timestamp mean no matching records in that accessible window. Tables reflect different activity; their latest timestamps need not coincide.

3. Inspect process evidence

let TargetId = "REPLACE_WITH_MDE_DEVICE_ID";
DeviceProcessEvents
| where Timestamp > ago(24h) and DeviceId == TargetId
| project Timestamp, ActionType, FileName, FolderPath, ProcessId,
          ProcessCreationTime, InitiatingProcessFileName, SHA1
| top 100 by Timestamp desc

The result is the latest 100 records, not an exhaustive history. Review ActionType and retain process creation time alongside PID; PIDs can be reused. A matching filename does not establish maliciousness, a loaded library, or persistence. Missing rows cannot prove a binary never ran.

Check field meanings and event types against the DeviceProcessEvents reference and the portal schema. Detailed command lines are omitted from this starter query to reduce incidental data collection.

4. Inspect network evidence

let TargetId = "REPLACE_WITH_MDE_DEVICE_ID";
DeviceNetworkEvents
| where Timestamp > ago(24h) and DeviceId == TargetId
| project Timestamp, ActionType, RemoteIP, RemotePort, RemoteUrl, Protocol,
          InitiatingProcessFileName, InitiatingProcessId, InitiatingProcessCreationTime
| top 100 by Timestamp desc

Keep ActionType: a network-related event is not automatically a successful application session. A destination address alone does not demonstrate data transfer, exploitation, or who controlled the destination. Correlate process identity and time with additional evidence as needed. See the DeviceNetworkEvents schema.

5. Make empty time buckets visible

let TargetId = "REPLACE_WITH_MDE_DEVICE_ID";
let WindowEnd = now();
let WindowStart = WindowEnd - 24h;
let Observed = union
 (DeviceProcessEvents | where Timestamp between (WindowStart .. WindowEnd)
  | where DeviceId == TargetId | project Timestamp, Kind="Process"),
 (DeviceNetworkEvents | where Timestamp between (WindowStart .. WindowEnd)
  | where DeviceId == TargetId | project Timestamp, Kind="Network")
 | summarize ProcessRows=countif(Kind == "Process"), NetworkRows=countif(Kind == "Network") by Bucket=bin(Timestamp,1h);
range Bucket from bin(WindowStart,1h) to bin(WindowEnd,1h) step 1h
| join kind=leftouter Observed on Bucket
| project Bucket, ProcessRows=coalesce(ProcessRows,0), NetworkRows=coalesce(NetworkRows,0)
| order by Bucket asc

This fills missing hourly buckets with zero counts across a rolling 24-hour window. The first and last buckets are partial hours. Counts describe query-visible process and network events, not a heartbeat or an availability percentage.

Investigate a gap by checking device activity, sensor reporting, permissions, retention, and ingestion timing. Do not label every quiet hour a sensor outage. Likewise, continuous events do not prove complete coverage of every security-relevant action.

Suggested finding format: “Within the specified window and accessible devices, these tables returned these observations. The following evidence remains missing.” Record the query, time window, device identity, and export limits with the result.

Real results can reveal device names, internal paths, IP addresses, and URLs. Keep exports in the authorized investigation workspace, not in a public issue or repository.
