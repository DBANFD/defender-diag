Going passwordless with Microsoft Entra ID

A practical field guide for planning, piloting, and rolling out passwordless authentication using Microsoft Entra ID, Windows Hello for Business, passkeys, FIDO2 security keys, Microsoft Authenticator, and Temporary Access Pass.

Choose the authentication outcome

A passwordless rollout needs a registration path, a daily sign-in method, and a recovery process. Decide which applications and users require phishing-resistant authentication before changing policy.

Passkeys (FIDO2) and Windows Hello for Business can satisfy Microsoft's phishing-resistant authentication strength. Authenticator phone sign-in is passwordless but is not in that strength. A Temporary Access Pass (TAP) can bootstrap registration and satisfy the MFA strength; it does not satisfy passwordless MFA or phishing-resistant MFA strengths. Conditional Access authentication strengths require Entra ID P1. See authentication strengths.

Prepare a small pilot and recovery route

  • Inventory sign-in requirements for browser apps, Windows, remote access, and administrative work. Success in one does not validate the others.
  • Select a small pilot group and record its existing policies and permitted methods.
  • Define identity verification for initial enrollment and lost-device recovery, including who can issue a TAP and how it is delivered.
  • Review overlapping Conditional Access rules so enrollment does not demand a credential the user has not registered yet.

Maintain at least two cloud-only emergency-access accounts using the tenant's onmicrosoft.com domain. Protect them with independently available strong authentication, such as FIDO2, and test and monitor their use. Exclude them from Conditional Access policies that could prevent emergency access; do not treat a long password alone as a complete design. Follow Microsoft emergency-access recommendations.

Use TAP for controlled enrollment

  1. Enable TAP for the pilot through the Authentication methods policy.
  2. Verify the person's identity, then issue a pass with an appropriate lifetime and single-use or multi-use setting.
  3. Have the user authenticate and register the approved method within the allowed session window.
  4. Test a new sign-in using that method, without relying on the TAP session.

Single-use TAP registration has a ten-minute window after sign-in. Longer device provisioning can require another single-use pass or an appropriately scoped multi-use pass. Choose deliberately rather than assuming one pass completes every Windows enrollment flow. A TAP does not replace the account password. See TAP configuration and limitations.

Register the method in the right place

Passkeys

Enable the permitted passkey types and restrictions for the target group. Check device and browser support, register through the supported Security info flow, and test a fresh authentication. Passkeys may be device-bound or synced; choose the permitted types according to the organization's requirements rather than treating every implementation as identical. See passkey policy and registration guidance.

Windows Hello for Business

Plan device enrollment, deployment policy, and the appropriate trust model. Hello provisioning occurs on the Windows device; it is not simply another Security info registration step. Validate on-premises resource access separately where required. See Windows Hello for Business deployment.

Authenticator phone sign-in

Enable the applicable Authenticator authentication mode and have the user configure phone sign-in. Push MFA registration alone does not establish passwordless phone sign-in. Number matching does not make this method phishing-resistant. See Authenticator passwordless sign-in.

Enforce gradually and test recovery

Start the intended Conditional Access policy in report-only mode and inspect actual sign-ins. Pilot enforcement only after registration and recovery work. Target the required resources and authentication strength, keeping the bootstrap route deliberate and limited.

  • Test a fresh allowed sign-in and verify the method and Conditional Access result in the logs.
  • Test a disallowed method and confirm it cannot satisfy the enforced strength.
  • Test loss of the primary authenticator, administrator-assisted recovery, and emergency access.
  • Check legacy and noninteractive workflows before removing existing methods.

Do not disable email OTP, security questions, or other methods indiscriminately: their use can differ between guest access, sign-in, and password reset. Document each dependency. If the pilot fails, restore the previous tested policy scope or state, preserve the logs, and correct the enrollment or application issue before expanding.
