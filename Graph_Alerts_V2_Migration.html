Migrating Microsoft Graph security alerts to v2

Check permissions, alert coverage, and collection behavior before trusting a migrated integration.

Reviewed: 3 November 2026.

What changed

The legacy /security/alerts endpoint retired on 15 October 2026. Microsoft states that it stops returning data after retirement. Move consumers to /security/alerts_v2; this also requires reviewing permissions and the response model. Microsoft migration guidance.

Start by finding every consumer: scheduled exports, ticket creation, dashboards, and scripts that quietly treat an empty response as success. Assign an owner to each integration before changing it.

Separate access from collection

The least-privileged read permission is SecurityAlert.Read.All for delegated or application access. Delegated access also requires an appropriate user role. Add the required permission and obtain administrator consent; the legacy SecurityEvents.Read.All scope is not a substitute. Incident access uses separate permissions.

GET https://graph.microsoft.com/v1.0/security/alerts_v2

Use an authenticated Graph client. Keep tokens outside logs and saved request examples. For supported query options, response fields, and permissions, use the alerts_v2 API reference.

Check coverage and meaning

The new endpoint is not a one-to-one replacement for every legacy source. Sentinel coverage requires the workspace to be connected to the Defender portal; standalone and tuned alerts need separate consideration. Review the migration guide against the sources your integration actually needs.

Update mappings for typed evidence instead of assuming the legacy state collections still exist. Keep alert IDs, timestamps, source, status, and incident relationships distinct. Compare representative records in the source portal and destination system, rather than expecting aggregate counts from different APIs to match.

Make collection failures visible

  1. Follow every @odata.nextLink returned by the API. A first page is not a complete collection.
  2. Choose a bounded collection window and record its UTC boundaries. For recurring collection, use a supported update-time filter and a small overlap to catch late updates.
  3. Deduplicate by alert identity and update existing destination records when the source changes.
  4. Advance the saved collection position only after every page and downstream write succeeds.
  5. Report authentication, permission, throttling, and transport errors separately from a successful response with no matching alerts.

Exercise the integration with an existing alert, an updated alert, multiple pages, and a recoverable failure. Record which sources are covered and route remaining gaps to an explicit owner. These are suggested acceptance checks for the integration, not extra API guarantees.
