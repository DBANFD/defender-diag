When Defender Antivirus stays disabled

A Windows Server 2016 investigation covering evidence, engine state, diagnostic commands, and next steps.

Technical review: 2 November 2026 · Checked against Microsoft documentation. Commands and deployment flows have not been validated in a live customer environment as part of this review.

What the evidence establishes

Investigation status: The original case notes describe an onboarded Windows Server 2016 device whose antivirus protection was not active. They do not establish a confirmed root cause or a successful repair.

Onboarding to Microsoft Defender for Endpoint (MDE) and running Microsoft Defender Antivirus are separate conditions. A reporting endpoint sensor does not prove that real-time antivirus protection is running. Start by identifying the intended antivirus product and collecting current local state.

This revision corrects the earlier interpretation of an internal PassiveMode = 2 value. It is not used here as proof of passive, disabled, or EDR-only operation. Those states are not interchangeable.

The raw logs have not been independently rechecked for this review. Do not mark policy, tamper protection, third-party software, or component health as ruled out from these observations alone.

Collect current state first

Run these read-only checks in an elevated Windows PowerShell session on the affected server. Record the time and retain errors as evidence. A missing cmdlet, property, or event log is itself a finding; it is not a reason to assume a healthy state.

Get-Date -Format o
Get-MpComputerStatus | Select-Object AMRunningMode, AMServiceEnabled,
    AntivirusEnabled, RealTimeProtectionEnabled, IsTamperProtected,
    AMProductVersion, AMEngineVersion, AntivirusSignatureVersion,
    AntivirusSignatureLastUpdated
Get-Service -Name WinDefend, Sense -ErrorAction Continue |
    Select-Object Name, Status, StartType
Get-WindowsFeature -Name Windows-Defender
Get-ItemProperty -LiteralPath 'HKLM:\SOFTWARE\Policies\Microsoft\Windows Advanced Threat Protection' -Name ForceDefenderPassiveMode -ErrorAction Continue
Get-WinEvent -LogName 'Microsoft-Windows-Windows Defender/Operational' -MaxEvents 50 |
    Select-Object TimeCreated, Id, LevelDisplayName, Message

Compare AMRunningMode with real-time protection and service status. Keep sensor health, antivirus mode, policy results, and portal freshness as separate checks. A missing ForceDefenderPassiveMode value does not establish the effective mode.

Choose the branch that matches the intended design

  • Defender should be primary: confirm the Defender feature is installed, required updates are present, and any previous antivirus was removed using its supported procedure. Inspect effective policy and the events around startup failures.
  • Another antivirus should be primary: confirm that product is healthy and that the supported Defender coexistence configuration is intentional. Passive mode requires the modern unified MDE solution on Server 2016.
  • Feature installation fails: follow the Server 2016 component-repair investigation before repeating onboarding.

Active antivirus, passive antivirus, disabled antivirus, and EDR in block mode provide different capabilities. EDR in block mode does not replace all active antivirus protections. See Defender Antivirus compatibility and modes.

Do not assume Windows client antivirus-detection behavior applies to Server 2016. Microsoft documents that installing another antivirus does not automatically disable Defender on this server OS. See Defender on Windows Server.

Use supported remediation

For an onboarded server that should run Defender as primary, Microsoft documents ForceDefenderPassiveMode = 0 under HKLM\SOFTWARE\Policies\Microsoft\Windows Advanced Threat Protection and a restart when returning from the relevant passive/disabled scenario. Confirm the prerequisites and management source before changing it. Value 1 requests passive mode; it is not a generic repair setting.

Platform version, onboarding history, policy, and tamper protection affect transitions. Use the current Windows Server configuration guidance for the applicable case. Do not edit undocumented status values, force protected-service startup settings, or use repeated offboarding as the default fix.

Troubleshooting mode and tamper protection

The earlier article incorrectly described -DisableTamperProtection as unsupported. Microsoft's current troubleshooting-mode procedure includes Set-MpPreference -DisableTamperProtection $true after troubleshooting mode is active on a supported device. This is a temporary diagnostic action, not an ordinary policy setting.

Server 2016 requires the modern unified solution and the documented sensor, platform, and engine minimum versions. A visible portal button alone does not prove eligibility. Confirm activation, check IsTamperProtected, and follow the time limit and restoration behavior in Enable troubleshooting mode. Use it only when the investigation requires a protected-setting change.

Also, the Server 2016 Windows Security interface can display inaccurate real-time protection status when tamper protection is enabled. Corroborate it with local PowerShell state; see tamper protection guidance.

Close the case with evidence

After the approved change and any required restart, repeat the collection. For a primary Defender deployment, expect normal antivirus operation and enabled real-time protection, current security intelligence, and no recurring startup error. Check the intended settings individually, then confirm fresh MDE telemetry and updated portal state.

Record what changed, before-and-after output, elapsed time, and remaining failures. If the service still cannot start, preserve the event and support diagnostics for escalation. A clean SFC result or a successful onboarding command alone does not close this case.
