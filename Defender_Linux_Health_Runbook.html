Defender on Linux: a health-check runbook

Check installation, antivirus mode, definition health, and cloud connectivity as separate questions.

Establish the intended state

Before changing anything, confirm the Linux distribution, kernel, Defender package version, and intended active or passive antivirus design. Check the current supported prerequisites for the deployed release rather than assuming a Windows procedure applies.

This runbook uses the local mdatp command. Use an authorized shell on the affected endpoint; elevate individual commands if required by the installed version and local permissions. A running process is one signal, not a full health assessment. See the Linux product documentation.

Collect health and connectivity

Download the Bash checklist · Inspect source

bash ./linux-defender-checks.sh

The helper runs the commands below without altering protection settings. The connectivity test sends requests to Defender cloud endpoints. Output can contain tenant identifiers, device identifiers, and network details; keep the real output private.

date -u '+%Y-%m-%dT%H:%M:%SZ'
mdatp health
mdatp connectivity test

If mdatp is missing, verify installation and PATH. If a command fails, retain the error and exit status. Exit zero from the helper only means the commands completed; inspect their returned health and test results before judging the endpoint.

Interpret health by component

FieldWhat to check
healthy / health_issuesRead the summary and any reported issues. Do not discard issues because another field looks normal.
licensedMicrosoft defines this as onboarded to a tenant. Confirm the intended tenant separately; this is not a license-entitlement audit.
passive_mode_enabledCompare with the intended coexistence configuration.
real_time_protection_available / enabledAvailability and enablement answer different questions. Active protection should match the intended design.
definitions_status / definitions_updatedReview both status and update time; updating can be transient.
app_version / product_expirationCheck the deployed package and its support state.

Property availability can vary by platform and version. Use mdatp health --help for supported detail views. Refer to Microsoft's health-field definitions for exact meanings.

Synthetic interpretation: healthy=true together with passive_mode_enabled=true does not establish active antivirus prevention. Confirm whether passive operation was intended before changing it.

Handle failed connectivity separately

When connectivity checks fail, investigate the specific failing endpoint, DNS, proxy path, firewall, and HTTPS inspection. Use the current documented service endpoints for the tenant's connectivity configuration. Do not hard-code an old endpoint list or disable TLS verification to make a test pass.

Microsoft's Linux connectivity troubleshooting explains the built-in test and common network causes. Passing it shows the tested paths worked at that time; confirm fresh endpoint reporting in the portal separately.

Choose the next diagnostic

  • Installation problem: inspect package-manager results and the Defender installation log. Follow the installation troubleshooting guidance.
  • Unexpected passive mode: identify the intended primary antivirus and management policy before making a mode change.
  • Unavailable real-time protection: inspect reported health issues and platform prerequisites. Do not compensate by adding broad exclusions.
  • Definitions remain unavailable: correlate update state with connectivity and package health, then retry the supported update path only after identifying the blocker.

Collect diagnostics and verify recovery

If escalation is required, Microsoft's documented collection command is:

sudo mdatp diagnostic create

This creates a local diagnostic archive; it does not publish it. Review and transfer it only through an approved support channel. If debug logging is needed, record the prior setting, limit the reproduction period, and restore the approved logging level. See Linux diagnostic resources.

After remediation, repeat the original checks, verify the intended protection mode, and confirm fresh portal telemetry for the correct endpoint. Record before-and-after evidence and remaining issues. Do not claim that a successful reinstall or a single healthy field proves the full workload is protected.
